# 0006 · 适配器只认三个动作，不碰数据库

状态：已采纳（2026-11-15）
取代 0002 里"投递 adapter 各自读队列"的含糊说法。

## 背景

第一版里 DSH 插件直接打开 SQLite，读待投、投完自己 `UPDATE state='delivered'`。
单机单消费者时这没问题——但它是**第二个写者**：

- 别人要给自己的 agent 写适配器，得连表结构、状态机、WAL 并发一起照抄
- 我们改一次 schema，所有适配器一起坏
- 跨语言（Python / Go）成本高得离谱

## 决定

队列归守护进程独占。适配器只通过三个 HTTP 动作与它说话：

| 动作 | 语义 |
|---|---|
| `take` | 取一批，拿小票（租约） |
| `done` | 投完了，点名的标已投，没点名的放回 |
| `retry` | 没投成，整张退回并记原因 |

三条不改的判断：

1. **小票互斥**：同一批不会被两个适配器同时拿走（哪怕并发）。
2. **租约到期自动收回**：适配器崩了、网断了，消息不会被锁死。
3. **DSH 插件本身就用这三个动作**——它没有特权，所以谁能用、好不好用，我们自己是第一个用户。

## 代价

- 每批多两次本地 HTTP 往返（实测 1–2ms，投递间隔 500ms，忽略不计）。
- 守护进程成为单点：它停了就不能取货。但采集和入库照常，恢复后照投，不丢。

## 后果

- 别人接自己的 agent：五十行，不需要读我们的任何源码。
- 队列 schema 变成纯内部细节，可以自由演进。
- `src/plugin/api-client.js` 是参考实现；`test/api-client.test.js` 是契约测试。
